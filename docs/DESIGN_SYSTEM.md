# DataMind Design System 視覺規範

> 這份文件是 DataMind 前端的**視覺設計規範(design spec)**,定義「我們的介面長什麼樣、為什麼這樣、規則是什麼」。
>
> **它不是實作指令。** 它不規定要改哪個檔案的哪一行。實作方式(要不要改 Vuetify 主題、token 放哪、用什麼 class)由開發者或 Claude Code 讀完規範後**自行判斷**。文件中出現的「實作提示」只是方向建議,不是硬性規定。
>
> 適用對象:團隊成員、Claude Code。任何人要開發或修改 DataMind 的 UI,先讀這份。

---

## 0. 技術脈絡(現況)

目前前端為 **Vuetify 4 + Tailwind CSS 4 並存**,靠 CSS layers 排優先權:

- Vuetify 4 負責元件與互動邏輯,`vuetify.ts` 定義 light / dark 兩套色票與 breakpoints,關閉內建 utilities(`utilities: false`)
- Tailwind 4 負責 utility(版面/間距),CSS-first config,用 `@theme` 把 Vuetify 的 CSS 變數橋接成 Tailwind `--color-*` token → **色彩與圓角是單一 source of truth**
- Layer 排序:`vuetify-core → vuetify-components → vuetify-overrides → vuetify-utilities → tailwind → vuetify-final`
- 字型 Roboto(僅覆蓋英數,中文走系統 CJK fallback,見 §3);圖示見 §3.5

> **色彩/圓角維持單一 source of truth。** 不透明的色值只定義在 `plugins/vuetify.ts` 的 theme,`styles/tailwind.css` 的 `@theme` 把它們橋接成 `--color-*` 供 CSS 使用。不要在 Tailwind 那邊另外寫死 hex,也不要在元件裡硬寫色值——那會退化成兩套各自維護的色票。
>
> **帶 alpha 或本身是漸層的值不進 Vuetify theme。** Vuetify 的 theme 插槽只吃不透明色(它會拆成 RGB 三個分量發成 `--v-theme-*`),所以玻璃 tint、頁面漸層色塊、標題光暈、畫布點紋這類值改放在 `styles/main.scss` 與 `styles/glass.css` 的 `.v-theme--light` / `.v-theme--dark` 兩個區塊裡,一樣是雙主題、一樣只有一份。判準很簡單:**能寫成單一 hex 的進 `vuetify.ts`,需要 `rgba()` / `linear-gradient()` / `transparent` 的留在 CSS。**
>
> **想看所有 token 實際長什麼樣,開 `/style-guide`**(只在 dev 模式掛路由)。色票、圓角、陰影、按鈕四變體、狀態徽章、對話氣泡、表格、骨架、AI 思考框都在上面,改 token 之後先去那頁確認。那頁右上角有主題切換鈕,兩個模式都要看過。
>
> **主題狀態由 `store/themeStore.ts` 持有,套用只在 `App.vue` 一處發生。** store 只管「現在是 light 還是 dark」(初值讀 localStorage,沒有就跟系統的 `prefers-color-scheme`),`App.vue` 用一個 `watchEffect` 呼叫 Vuetify 的 `theme.change()`,並把 `.v-theme--light` / `.v-theme--dark` 同步掛到 `<html>`。掛 `<html>` 是必要的:下拉選單、引用浮卡這類 `Teleport to="body"` 的浮層在 `.v-application` 外面,拿不到掛在那裡的主題變數,不同步的話它們會整組退回淺色。

## 1. 設計原則(判斷基準)

當規範沒有明講、需要臨場判斷時,回到這五個原則:

1. **內容為主,介面退位(Deference)** — 邊框、色塊、裝飾都是為了襯托資料(論文、欄位、分析結果),不跟內容搶注意力。有疑慮時,選更安靜的做法。
2. **清晰優先於美觀(Clarity)** — 任何視覺效果(玻璃、動畫、低對比)一旦犧牲可讀性就是失敗。文字對比至少符合 WCAG AA(一般文字 4.5:1、大字 3:1)。
3. **用層次建立引導(Depth)** — 用「前景/背景、陰影、玻璃、動畫」幫使用者理解「現在在哪一層、什麼重要」,而不是把所有東西平貼在同一平面。
4. **一致性可被學習** — 同一種元件、同一種互動,行為到處都一樣。使用者學一次,整個系統都會用。這是「設計系統」跟「一堆好看畫面」的根本差別。
5. **克制** — 「太雜」永遠比「太簡單」更常出問題。玻璃、強調色、動畫都是稀缺資源,只用在真正需要的地方。

## 2. 色彩系統

### 2.1 核心理念

- **藏青(navy)是品牌身份色**,用在主要動作、選中狀態、logo、重點圖示。它是整個系統的識別,不要讓其他同等飽和度的顏色跟它搶。
- **狀態色(綠/琥珀/紅)只表達「語意」**,不作裝飾。綠=成功/已對應、琥珀=待確認/警示、紅=錯誤/未對應。不要因為「想加點顏色」而用它們。
- **中性灰階**承載絕大多數的文字、邊框、背景。

### 2.2 色票(語意角色 → 建議值)

> 這裡定義「角色」與建議色值。實作時橋接成單一 token 來源(延續現有 Vuetify↔Tailwind 橋接模式)。色值可微調,但語意角色不要亂用。
>
> **表中的色值是淺色主題的。** 深色主題有各自的一組值,語意角色完全相同——見 §2.5。元件永遠只引用角色 token,不要引用這裡的 hex。

| 角色 token | 建議色值 | 用途 |
|---|---|---|
| `--color-ink` | `#1A3159` | 主品牌藏青。主要按鈕、選中、重點 |
| `--color-ink-strong` | `#12244A` | 深一階,hover/按下、標題強調 |
| `--color-ink-soft` | `#626B7E` | 次要文字、說明、icon |
| `--color-ink-vivid` | `#2B5CA8` | 藏青亮一階。`ink` 疊在深色內文旁分不出來時用(選單已選項、參考文獻標記、AI 思考框邊框) |
| `--color-text` | `#1C2130` | 主要內文 |
| `--color-surface` | `#FFFFFF` | 卡片、面板底 |
| `--color-surface-alt` | `#F1F4F8` | 次級底(表頭、hover 背景、工具列)。偏冷的淺灰藍,跟頁面漸層同色溫 |
| `--color-page` | `#E4E9ED` | 頁面底(玻璃漸層的基底,見 §5) |
| `--color-border` | `#E4E6E8` | 一般分隔線(hairline) |
| `--color-border-strong` | `#D3D8DC` | 強調分隔、輸入框邊界 |

| `--color-warning` | `#C88819` | 待確認/警示(圓點);文字用 `#835A07` |
| `--color-warning-bg` | `#F7EECF` | 警示徽章底 |
| `--color-danger` | `#D7445C` | 未對應/錯誤(圓點);文字用 `#A22F43` |
| `--color-danger-bg` | `#F2DEE2` | 錯誤徽章底 |
| `--color-score-low` | `#E6B800` | 期刊評分低分的進度條**填色**。對白底只有 1.87:1,**絕不可當文字色**(見 `utils/scoreColor.ts`) |
| `--color-inverted` | `#F1F5F9` | 深底上的反白文字(藏青按鈕、使用者氣泡)。**兩個主題同值**,見 §2.5 |
| `--color-ink-solid` | `#1A3159` | 「兩個主題都深」的實色底,專門承載 `--color-inverted`。深色主題另有深一階的值,見 §2.5 |
| `--color-ink-solid-deep` | `#1B2C4C` | 同一組實色底的暗端,只給漸層當第二個色停(結果洞察卡)。這個值是 `#1A3159` 混 70% 進 `#1C2130` 解出來的,但實作寫成定值——它跟 `--color-ink-solid` 沒有自動連動,調前者記得回來調它 |
| `--color-ai-from` / `--color-ai-to` | `#2B5CA8` / `#12244A` | AI 按鈕的漸層兩端。跟 `--color-ink-solid` 同一個性質:兩個主題都必須是深的 |

> **命名對照:本文件寫 `danger`,程式碼是 `error`。** Vuetify 主題有固定的 `error` 插槽名,為了不另立撞名的 key,實作沿用 `error`——`--color-danger` / `--color-danger-bg` 在程式碼裡實際叫 `--color-error` / `--color-error-bg`,文字色是 `--color-error-text`。語意完全相同,寫 code 時用 `error`。

**對話氣泡**(AI 助理、結果分析跟談)也由藏青推導,不另立色系:

| 角色 token | 建議色值 | 用途 |
|---|---|---|
| `--color-chat-user` | `#1A3159` | 使用者氣泡,實色藏青配 `--color-inverted` 白字(11.78:1) |
| `--color-chat-system` | `#FFFFFF` | AI 氣泡,純白配 `--color-text` |

> **AI 氣泡靠高度而不是明度差浮起來。** 曾經用藏青極淡 tint(`#DCE6F5`),但它跟玻璃面板底的明度差只有 1.09–1.20:1,得再補一道描邊才看得出邊界,疊起來很濁。現行做法改成純白 + 兩層投影(`0 1px 2px` 貼地 + `0 6px 16px` 擴散),讓氣泡像浮在玻璃上的紙片,不需要描邊。使用者氣泡是實色藏青,本來就不需要。
>
> 氣泡內的弱化文字(「思考中…」、開場白)用 `--color-ink-soft`。
>
> **深色主題的 AI 氣泡改靠明度差,不靠投影。** 兩層投影都是深藍(`rgba(14,30,66,...)`),在石墨底上等於不存在。深色把 `--color-chat-system` 換成次級底 `#26292D`,靠它跟玻璃面板的明度差撐出邊界——這是少數「淺色靠陰影、深色靠明度」的例子,新增類似元件時要記得深色下投影幾乎不會有作用。

> **`**粗體**` 標記會被渲染成真的粗體。** AI 回覆常帶 markdown 粗體標記,由 `utils/formatChatText.ts` 轉成 `<strong>`(只處理這一種標記,不做完整 markdown 解析,且會先跳脫 HTML)。字重是 700,屬於 §3 的唯一例外。

> **重要:金色已淘汰。** 早期版本曾用亮金色當強調色,已確認不採用。琥珀(`--color-warning`)只作狀態色,不當品牌強調。
>
> **圓點色跟文字色刻意不同一個值。** 圓點是實色小面積,直接用 `--color-success`/`--color-warning`/`--color-danger` 沒問題;但文字疊在對應的 `-bg` 淺色徽章底上時,同一個值對比不夠(量過只有 4:1 上下),所以文字一律用表中標的更深值,確保跟徽章底過 §2.4 的 WCAG AA 4.5:1。之後要調任何狀態色,記得兩個值一起檢查對比,不要只改圓點色。
>
> **三組狀態色往冷調重新調配過**(2026-08)。原本偏暖高飽和的一組(綠 `#1F7A44`、琥珀 `#C9822E`、紅 `#C7392E`)疊在冷色藏青主題與頁面漸層上顯得突兀,綠的色相推到青綠(163°)、紅推到玫瑰紅(350°),兩者都往冷側靠;徽章底同步抽掉暖黃、補一點冷灰。
>
> **琥珀後來又往回調了兩次。** 跟著上面一起降飽和之後,它疊在白底表格上彩度太低、幾乎讀不出是有顏色的——暖黃色系在高亮度下本來就比冷色系更容易被看成灰或米色,這是綠、紅不會遇到的問題。先拉高飽和度並讓色相略偏橙,看過畫面後覺得偏橙不如偏黃,再把色相調回更黃的 38–46°、徽章底提亮。結論記在這裡:**調狀態色時不要三色套用同一組飽和度規則**,琥珀需要比另外兩色更高的飽和度才讀得出來。

**量到的對比**(調整任何狀態色時三組都要重驗):

| 檢查項 | 值 | 門檻 |
|---|---|---|
| `#1D6151` on `#DCEAE5`(成功徽章文字) | 5.88:1 | AA 文字 4.5:1 ✅ |
| `#835A07` on `#F7EECF`(警示徽章文字) | 5.27:1 | AA 文字 4.5:1 ✅ |
| `#A22F43` on `#F2DEE2`(錯誤徽章文字) | 5.40:1 | AA 文字 4.5:1 ✅ |
| `#3B9A7F` on 白(成功圓點) | 3.43:1 | 圖形 3:1 ✅ |
| `#C88819` on 白(警示圓點/星號) | 3.00:1 | 圖形 3:1 ⚠️ 剛好貼線 |
| `#D7445C` on 白(錯誤圓點) | 4.31:1 | 圖形 3:1 ✅ |

> 警示圓點只有 3.00:1,**剛好卡在門檻上,不要再提亮**。它同時用在 [MappingTable.vue](../frontend/src/components/hub/fieldMapping/MappingTable.vue) 的預測目標星號上,那是純圖形沒有文字輔助,再淡就不合格了。徽章底(`-bg`)不受圖形門檻限制,所以可以做得比圓點淺得多。

### 2.3 Workflow 節點配色(分類色,非深淺)

Workflow 節點依**在 pipeline 裡扮演的角色**分五類,每一類一個顏色(類似 Orange ML pipeline),而非同色深淺。

**五類色票**(低飽和大地色系,比照 Orange Data Mining 六類配色的大致順序——橘/藍/紫/綠/紅——指派給五個分類):

| 分類 token | 色值 | 涵蓋節點 |
|---|---|---|
| `--color-node-source` | `#D2A596` 灰橘棕 | File、Data Table |
| `--color-node-transform` | `#8EB8D1` 灰藍 | Preprocessor、Feature Engineering |
| `--color-node-visualize` | `#A9AED6` 灰藍紫 | Distribution |
| `--color-node-model` | `#85BDBC` 灰青綠 | Settings、Models |
| `--color-node-evaluate` | `#CFA3B6` 灰玫瑰 | Test & Score、Feature Importance、Confusion Matrix、Compute CI |

> 這五個分類色跟 success/warning/error 三個狀態色的色相距離**沒有**嚴格要求。分類色統一走圓形節點底色,狀態色統一走節點外部的徽章/spinner,兩者的區隔靠**構造與位置**,不是靠色相隔開。
>
> 深色 icon(`--color-ink-strong`)疊在五個淺底色上,節點另加一圈細邊框,靠淺底 + 邊框 + 深色 icon 的構造本身撐開跟畫布、跟彼此的對比,不是靠色相跨度。
>
> **五個色值兩個主題共用,但構造要翻面。** 深色主題沿用「粉彩底 + 深色 icon」會失敗:`--color-ink-strong` 在深色是淺藍,疊在粉彩底上幾乎看不見。深色的構造是**分類色淡染的深底 + 亮一階的分類色 icon**——底用分類色混 24% 進 `--color-surface`,icon 用分類色混 82% 進白,邊框用分類色混 58% 進 `--color-surface`。色相不變,所以 Orange 那套配色識別在兩個主題都成立,變的只有明暗關係。
>
> **但深色的識別幾乎全靠 icon,不靠底色。** 五個底色解出來是 `#453E3E` / `#37424A` / `#3D404B` / `#364345` / `#453E44`——彼此非常接近,把分類色混進石墨底本來就會把色差壓掉。這是刻意的取捨(底色太飽和會讓畫布變成五顆彩球),代價是深色下要看 icon 才分得出類別。之後若覺得不夠分,調的是 icon 那一階(混白的比例),不是底色。

節點是圓形淺底 + 深色 icon,節點間用連接線串起(見 §7.6)。新增節點時歸到既有五類之一,不要為單一節點另開顏色;真的需要新分類再回來更新此表,不要各畫面各自上色。

> **這個專案沒有「AI 分析」節點。** `mdi-brain` 那顆是 Models(機器學習模型),不是 LLM 分析。早期版本的分類表把「AI / 模型分析」「人工確認」「完成」當成節點類型,那是誤解——後兩者是執行狀態不是類型,已於此次改版修正。

### 2.4 對比要求

- 文字/背景對比一律過 WCAG AA。
- 低飽和背景(玻璃、淺色底)上的文字,寧可加深文字或加半透明底襯,**不要用深色文字陰影救對比**。

> **唯一例外:淺底上的白色 offset/blur。** 頁面標題疊在 §5.4 的漸層上時,可用白色 `text-shadow`(如 `0 1px 0 rgba(255,255,255,0.9), 0 2px 8px rgba(255,255,255,0.65)`)把字周圍打亮。這跟被禁止的做法方向相反:深色陰影是在深底上描邊、假造出對比的錯覺;白色打亮是實際提高文字周圍的明度,對比是真的變好。只用在頁面標題這種疊在漸層上、沒有卡片墊底的文字,不要拿去救內文。
>
> **這個例外只存在於淺色主題。** 深色主題把光暈設成透明(`--title-halo-near` / `--title-halo-far`),不改成暗色版本:白光暈在深底上會讓字糊掉,暗光暈則只是把字周圍弄髒,兩種都沒有提高對比。深底本來就跟淺色標題有足夠明度差,不需要救。

### 2.5 深色模式

深色主題不是把淺色反相,是**同一組語意角色換一套值**。元件永遠只引用角色 token,兩個主題就會一起成立;元件裡寫死 hex 或 `rgba()`,深色就一定漏。

**色票對照**(語意角色與 §2.2 完全相同,只列有差異的):

| 角色 token | 淺色 | 深色 | 說明 |
|---|---|---|---|
| `--color-ink` | `#1A3159` | `#8FB4EE` | **翻成淺藍**。深底上要維持 4.5:1 就不可能沿用深藏青;色相留在 220° 附近,兩個模式仍是同一個品牌 |
| `--color-ink-strong` | `#12244A` | `#B4CDF5` | 同上,亮一階 |
| `--color-ink-vivid` | `#2B5CA8` | `#5B8FD8` | |
| `--color-ink-soft` | `#626B7E` | `#9BA1A8` | |
| `--color-text` | `#1C2130` | `#E8EAEC` | |
| `--color-surface` | `#FFFFFF` | `#1F2225` | |
| `--color-surface-alt` | `#F1F4F8` | `#26292D` | 深色的次級底比 `surface` **亮**一階,淺色是暗一階——方向相反,但語意都是「比卡片底再退一層」 |
| `--color-page` | `#E4E9ED` | `#141618` | |
| `--color-border` | `#E4E6E8` | `#33373C` | |
| `--color-border-strong` | `#D3D8DC` | `#454A50` | |
| `--color-success` / `-bg` / `-text` | 見 §2.2 | `#4FC79E` / `#16342B` / `#6ADCB6` | 三組狀態色都提亮、徽章底翻深,語意不變 |
| `--color-warning` / `-bg` / `-text` | 見 §2.2 | `#E0A93F` / `#3A2E12` / `#F0C46A` | |
| `--color-danger` / `-bg` / `-text` | 見 §2.2 | `#F0687F` / `#3A1D25` / `#FF8FA2` | |
| `--color-chat-user` | `#1A3159` | `#2B5CA8` | 實色藏青亮一階,仍配 `--color-inverted` |
| `--color-chat-system` | `#FFFFFF` | `#26292D` | 深色的 AI 氣泡改走次級底,不再靠純白 + 投影 |
| `--color-ink-solid` | `#1A3159` | `#2F5288` | 見下方「實色深底」 |
| `--color-ink-solid-deep` | `#1B2C4C` | `#1F3A63` | |
| `--color-ai-from` / `--color-ai-to` | `#2B5CA8` / `#12244A` | `#2C4A86` / `#1C3358` | AI 按鈕漸層,兩端在兩個主題都是深的 |
| `--color-inverted` | `#F1F5F9` | `#F1F5F9` | **刻意兩個主題同值**,它的定義就是「疊在深底上的淺字」,而深底在兩個主題都是深的 |
| `--color-node-*` | 見 §2.3 | 同值 | 構造翻面,色值不變,見 §2.3 |

**只在深色主題有的規則:**

- **實色深底一律用 `--color-ink-solid`,不要用 `--color-ink`。** 這是深色模式最常犯的錯:`ink` 在深色翻成淺藍,凡是「藏青底配白字」的地方(主要按鈕、勾選框、切換 pill、選中的分頁、洞察卡、tooltip)都會變成淺字疊淺底。`--color-ink-solid` 的定義就是「兩個主題都深、可以承載 `--color-inverted`」,深色值 `#2F5288` 對 `#F1F5F9` 是 **7.14:1**。
  - 但是 `background: var(--color-ink); color: var(--color-surface)` 這種寫法**本來就是對的**,因為文字也跟著翻面。要判斷的是文字色會不會跟著走,不是看到 `ink` 就換掉。
- **`color-mix(..., white)` 不能用在會隨主題變的地方。** 這類「調淡」的寫法在深色下會把色塊往白色拉,變成一塊亮斑。改成混 `var(--color-surface)`——淺色主題的 `surface` 正好是 `#FFFFFF`,所以淺色的輸出完全不變。
- **原生控制項要靠 `color-scheme`,而且不用自己寫。** `<select>`、`<input>`、捲軸的配色由瀏覽器決定,一般 CSS 蓋不掉,只吃 `color-scheme`。**Vuetify 已經對 `.v-theme--light` / `.v-theme--dark` 各發了一條 `color-scheme`**(`composables/theme.js`,包在 `vuetify-utilities` layer 裡,排在 `vuetify-overrides` 之後),而那兩個 class 現在也掛在 `<html>` 上,所以整棵樹連同 Teleport 出去的浮層都涵蓋到了。**專案這邊要做的只有一件事:不要在元件裡寫死 `color-scheme: light`**——曾經有 10 處這樣寫,把整條規則擋掉了。也不要自己再補一條 `.v-application { color-scheme: ... }`,它會輸給 Vuetify 那條,是死碼。
- **半透明的白色填色要換成 token 或 `color-mix`。** `rgba(255,255,255,0.x)` 當底在深色下是一片霧,改用 `color-mix(in oklab, var(--color-surface) N%, transparent)`(淺色輸出同樣不變),或另立一組雙主題變數(玻璃見 §5.2)。
- **兩個主題共用的色塊,構造可以不同。** 節點(§2.3)、骨架屏掃光(淺色往白衝、深色只提一階,再亮會變成刺眼白閃)都是這個模式:語意一樣,明暗關係反過來。

> **深色不是「淺色的附屬」,但淺色是既有基準。** 這輪加深色模式時的硬性要求是**淺色的畫面必須與改動前一模一樣**,絕大多數替換都挑了「淺色輸出等值」的寫法(混 `--color-surface`、`--glass-*` 沿用原數值)。之後再動這些 token,同樣要兩個主題一起看過。
>
> **刻意沒有維持淺色原樣的地方,完整清單:**
>
> | 位置 | 改了什麼 | 為什麼 |
> |---|---|---|
> | 論文頁檢視/編輯切換鈕 | 收斂到共用的 `--glass-*`,比原本厚一階 | 它本來就屬 §5.3 的浮動元件,該吃共用玻璃 |
> | Settings 精靈頁籤的號碼圓圈 | 白字疊粉彩 → 比照 §2.3 的節點構造 | 原本對比只有 1.92–2.00,兩個主題都不合格 |
> | Settings 精靈作用中頁籤的文字 | 分類色 → 分類色混 50% 內文色 | 原本 1.90–1.99,同上;混過之後淺色 5.8–6.0、深色 9.1–9.3,色相仍讀得出來 |
> | Settings 精靈作用中頁籤 | 加一圈分類色描邊、字重 500 → 700 | 深色下光靠底色差分不出作用中是哪一格(見 §3 例外三) |
> | 專案卡片的刪除鈕 | `color: white` → `--color-surface` | 深色的 `--color-error` 提亮後,白色圖示只剩 3.00:1 貼在門檻上 |
> | `/style-guide` 的背景漸層示範 | 自己一組 rgba → `--page-tint-*` | 展示頁的用途是核對真實樣式,不該自己另外寫一份 |
>
> 除了第一列,其餘全是**既有的淺色缺陷被深色模式照出來的**。**發現這類跨主題共通的缺陷時,修它,不要為了保持淺色不變而把錯誤留下來**——但一定要在這張表裡記一筆,否則「淺色沒動過」這個基準就失效了。

## 3. 字體

- 介面字型:Roboto(透過 `unfonts.css` 載入),對應 token `--font-body` / `--font-heading`。
- **Roboto 只覆蓋英數字元。** 它沒有中文字形,瀏覽器逐字元 fallback,所有中文字實際上是由系統 CJK 字型畫的(各作業系統不同)。畫面上九成是中文,所以整體觀感由系統字型決定,不要以為調 Roboto 就能改變中文的樣子。
- **不使用等寬字型。** 欄位名、type、class 等 identifier 一律用一般內文字型,靠位置與標籤區隔,不靠字型。曾經有過 `--font-mono`(Roboto Mono)並用在表格 identifier、變數清單、設定輸入框,已於 2026-08 全數移除 —— 等寬字在以中文為主的介面裡只會讓英數突兀,中文本來就沒有等寬版本,兩種字型混排反而更亂。
- 只用兩種字重:**Regular 400** 與 **Medium 500**。不用 600/700 — 過重會與安靜的整體調性衝突。
  - **例外一:AI 對話氣泡裡 `**粗體**` 標記轉出的 `<strong>`。** user 實際比對 400/500/700 三版後,700 才看得出「這裡在強調」,500 太接近內文分辨不出來。僅限對話氣泡文字內的強調,不要擴大套用到其他元件。
  - **例外二:「資料強調」的 700**——展示型數字、資料表格裡的最佳值/重點結果、資料表格表頭,見下表。跟例外一互相獨立:一個標示「這是重點數據」,一個標示「AI 在強調語氣」,不要合併成同一條規則。
  - **例外三:Settings 精靈作用中的頁籤。** 這是唯一一個非資料、非對話的 700——導覽元件靠底色跟其他分頁區分時,深色主題下的明度差不夠,字重要一起分擔辨識;實作見 §7.6。要再開這種例外之前,先確認底色與描邊都已經用盡。
  - 三個例外的共同判準:**這個字要承擔「掃視時第一眼落點」的功能**,而不只是比旁邊重要一點。純粹想強調的地方仍然用 500。

| 角色 | 大小 | 字重 |
|---|---|---|
| 展示型數字 | 32px | 700 |
| 頁面標題 h1 | 22px | 500 |
| 區塊標題 h2 | 18px | 500 |
| 小標 h3 | 15–16px | 500 |
| 內文 | 14px | 400 |
| 次要/說明 | 13px | 400 |
| 標籤/徽章 | 11–12px | 400–500 |
| 表格最佳值/重點結果 | 隨內文 | 700 |
| 資料表格表頭 | 12px | 700 |

- **展示型數字**專指儀表板統計數字這類「一眼要看到的單一數值」,用 `--color-ink` 藏青讓它成為畫面錨點。它不是標題,不要拿來放文字。
- 一律**句首大寫(sentence case)**,不用 Title Case、不用全大寫。
- 欄位名、type、class 等 identifier 不用粗體強調,也不用等寬字型(見上)。

## 3.5 圖示(Icon)

### 3.5.1 核心規則

- **圖示庫沿用現有 `@mdi/font`(Material Design Icons)**,不換庫、不混用其他圖示字體或 SVG 圖示集。
- **一律用線框(outline)版本**,例如 `mdi-account-outline` 而不是 `mdi-account`。線框筆畫輕、視覺重量小,跟這套系統「安靜、不搶內容」的整體調性(見 §1 Deference、Clarity)比實心圖示更搭 — 實心圖示色塊感重,在藏青為主的介面裡容易意外變成視覺焦點。
- 找不到 `-outline` 版本的圖示(MDI 有些符號本身沒有實心/線框兩種變體,例如 `mdi-plus`、`mdi-close`、`mdi-arrow-left`、`mdi-chevron-right` 這類純符號,本身筆畫就是線條化的),直接用該圖示本身即可,不受這條規則限制。
- 同一個語意只挑一個圖示、全站共用,不要幾個地方各自選了不同但意思相近的圖示(例如都是「上傳」,不要有的地方用 `mdi-upload-outline`、有的地方用 `mdi-tray-arrow-up`)。

### 3.5.2 現況與遷移

目前全站(`frontend/src/`)有 107 處圖示引用,只有 26 處(24%)是線框版,其餘 81 處是實心版,而且有實際的混用案例(`mdi-upload` 與 `mdi-upload-outline` 同時存在)。這份規則從現在開始適用於新寫的程式碼;既有的 81 處實心圖示**不在這次一次換掉**,留到之後逐頁/逐元件套用設計系統時,經過的地方順手換成線框版即可,不用另開一輪專門的圖示替換工作。

### 3.5.3 尺寸

不特別另訂圖示尺寸 token。沿用各元件情境既有的 `size` 用法即可(例如按鈕內圖示、狀態圖示等,依所在元件的字級抓對應大小),沒有統一數值的必要 — 圖示是搭配文字/元件出現,尺寸應該跟著情境走,不是獨立的設計決策點。

## 5. 玻璃效果(Glassmorphism)規範

玻璃是這套系統的特色,但**最容易做壞**。核心規則:

### 5.1 三個必要條件(缺一玻璃就失效)

1. **背後要有東西透出來** — 玻璃層下方必須有漸層色塊/彩色光斑的環境,否則模糊等於白做,只剩一個半透明方塊。頁面底(`--color-page`)應鋪一層柔和的多點徑向漸層(藏青為主、極少量暖色點綴),見 §5.4。
2. **半透明 + 模糊並存** — 只有模糊沒有透明,或只有透明沒有模糊,都不是玻璃。
3. **文字要有底襯** — 玻璃層要疊一層 10–30% 的白色/深色 tint,讓文字對比足夠。

### 5.2 參數建議

- 模糊值 **10–16px** 就好(busy 背景可到 20px 上限)。過高會糊、傷效能。
- 玻璃底 tint:淺色玻璃用 `rgba(255,255,255,0.4~0.7)`;深色玻璃用 `rgba(13~24, 14~27, 16~31, 0.6~0.9)` 的石墨色。
- 邊框:淺色上緣用較亮的 `rgba(255,255,255,0.6~0.85)`模擬受光邊,其餘 `rgba(255,255,255,0.5)` 左右;深色的白邊要壓到 `0.09~0.18`,照淺色的強度會變成一圈刺眼的白框。
- 一律加 `-webkit-backdrop-filter` 前綴,並提供 `@supports` fallback(不支援時退回較高不透明度的純色底)。

> **深色玻璃的方向跟淺色相反。** 淺色是「面板比底色亮」,深色是「面板比底色暗」,靠 blur 把後面的內容暈進來當亮度來源。照搬淺色那組(面板比底色亮)在深色下會變成一層灰霧,把後面的顏色整個洗掉。
>
> **玻璃參數依用途分三組,不要硬收斂成一組。** 實作在 [glass.css](../frontend/src/styles/glass.css),三組都是雙主題:
>
> | 變數組 | 用在 | 為什麼要分開 |
> |---|---|---|
> | `--glass-tint-*` / `--glass-edge` / `--glass-sheen*` | 一般玻璃面板、浮動切換鈕 | 基準組 |
> | `--glass-menu-tint-*` / `--glass-menu-edge` | 下拉選單 | 選單多半開在實色卡上,`backdrop-filter` 透不出東西,要比基準組更不透明才撐得出層次(見 §5.3) |
> | `--glass-drawer-tint` / `--glass-drawer-edge` | workflow 底部抽屜 | 整片橫跨畫布,要比選單再透一階才不會壓掉底下的節點;深色反而要比淺色更不透明,石墨畫布上用淺色那個值會糊成一片看不出邊界 |
>
> **抽屜那組只有色值,不是完整的玻璃條目。** 它沒有走 `.glass-panel` / `.glass-menu`,模糊值、前綴、fallback 都寫在 `WorkflowWorkspace.vue` 自己的規則裡。只有一個消費者時這樣可以,但 §5.2 的「一律加前綴與 fallback」對它同樣有效——它曾經漏掉,是後來補的。
>
> 新的玻璃元件先試基準組,真的不合用再新增一組並在這裡記下理由——每多一組就多一份要同時維護兩個主題的成本。

### 5.3 用在哪(克制原則)

玻璃**只用在少數浮動/導覽性元件**,不是整頁玻璃化:

- ✅ 側邊欄(浮在漸層背景上)
- ✅ AI 對話面板(浮動、需要與背後內容區隔)
- ✅ 彈窗 / modal / 浮動工具列(如有)
- ✅ 下拉選單 / select 選單(浮在觸發元件上方的選項清單,屬於「浮動」的一種)
- ❌ 一般資料卡片、表格、內文區塊 — 用實色 `--color-surface`,不要玻璃

> **這兩條在下拉選單上互相牴觸,已知且刻意不解。** 下拉選單幾乎都開在實色白卡上,而 `--color-surface` 是不透明 `#FFFFFF`,§5.1 第一條(背後要有東西透出來)因此不成立——模糊一片純白還是純白,沒有任何 `backdrop-filter` 參數調得出玻璃。
>
> 現行做法是折衷:`.glass-menu` 自帶一道偏冷的半透明漸層當材質,在白卡上算出約 `#EBEFF3` 的層次讓選單浮得起來,邊框改冷灰(白邊在白卡上等於沒有),`backdrop-filter` 保留——選單下緣溢出卡片、蓋到頁面漸層時那一段仍是真透光。
>
> 根本解是讓承載卡片變成半透明,但那會牴觸本節「一般卡片不玻璃」這條,並牽動整個 Hub 的卡片視覺。要走那條路必須先改設計原則,不是實作層能自行決定的。

> **`JournalScoreDialog.vue` 的彈窗卡片已改成不用玻璃,直接用實色 `var(--color-surface)`。** 這個彈窗背後是一層深色半透明遮罩(`rgba(18, 30, 58, 0.45)`),`backdrop-filter` 疊在卡片上會把遮罩的深色一起糊進玻璃裡,結果不是通透的玻璃感,而是髒髒的濁白色。跟 2026-08-15 workflow 畫布那次的玻璃問題同一個根因,當時也是改成實色解決的。
>
> 這造成一個已知的不一致:同類型的 `InsertChartDialog.vue` 目前仍是 `.glass-panel`,背後也是同一種深色遮罩,推測會有一樣的濁白問題,但這次沒有動它,先記著,之後再處理。

### 5.4 背景漸層(讓玻璃可見的關鍵)

頁面底鋪多點徑向漸層,提供玻璃透光的顏色來源。現行實作在 [main.scss](../frontend/src/styles/main.scss):

```css
.v-application {
  background:
    /* 主色塊:窄而高的橢圓貼齊左緣，縱向蓋滿側邊欄供其透光，
       橫向在側邊欄右緣外就衰減完，讓頁面上方的標題帶落在近乎純底色的區域 */
    radial-gradient(520px 900px ellipse at 4% 60%, rgba(90, 130, 190, 0.50), transparent 70%),
    /* 右側色塊下移到視窗中段，同樣避開標題帶，留在浮動面板常駐的高度 */
    radial-gradient(640px circle at 92% 58%, rgba(110, 143, 178, 0.22), transparent 60%),
    /* 純裝飾暖色點，刻意不借用 --color-warning 的值 */
    radial-gradient(520px circle at 25% 92%, rgba(196, 150, 130, 0.10), transparent 55%),
    linear-gradient(175deg, #F4F7F9 0%, #E4EAEF 55%, #DCE3E9 100%);
  background-attachment: fixed;
}
```

> **蓋在 `.v-application` 而不是 `body`。** VApp 元件本身有不透明的 background,蓋在 body 上的話漸層完全看不到。
>
> **色塊位置是為了標題可讀性算過的,不要隨意搬動。** 頁面標題與副標沒有卡片墊底,直接疊在漸層上,所以兩個主色塊都刻意避開畫面上方的標題帶——左側那塊做成窄橢圓在側邊欄右緣外就衰減完,右側那塊下移到視窗中段。動到位置或濃度時要回頭確認標題還讀得清楚(§2.4 禁用深色 text-shadow 救對比)。
>
> 側邊欄要有明顯玻璃感,靠的就是左側那塊亮色落在它後方。
>
> **暖色點的色值跟狀態色系無關**,不要為了方便直接借用 `--color-warning` 或其他語意色的 hex——那樣一旦之後改狀態色,背景會跟著意外變色,也違反 §2.1「狀態色只表達語意,不作裝飾」的原則。
>
> **色塊的位置與大小兩個主題共用,只有顏色換。** 上面四個色停各自抽成 `--page-tint-primary` / `--page-tint-secondary` / `--page-tint-warm` / `--page-base`,深色給另一組值:主色塊降到 `rgba(62,98,160,0.18)`、次色塊 `rgba(52,74,116,0.13)`、暖色那層直接設成 `transparent`(在深底上根本看不出來),底色換成石墨漸層 `#171A1F → #131519 → #0F1114`。
>
> **深色的藍要壓得很低。** 石墨底摻一點品牌藏青是為了讓深色不是全然中性的灰,但濃度再高一點色塊的邊界就會被看出來,變成兩坨藍斑而不是一層底。曾經試過中性灰版本(完全不摻藍),看起來太冷太死,才調成現在這個克制的量。
>
> 畫布區另外疊一層 `--canvas-veil` 把漸層壓淡(淺色是半透明白、深色是半透明黑),Hub 那邊的濃度直接鋪在畫布上太重。

## 6. 動畫 / Motion 規範

動畫目的:讓系統**流暢、有回饋、有引導**,不是炫技。每個動畫都要能回答「它幫使用者理解了什麼」。

### 6.1 Motion tokens

統一時長與緩動,不要每個元件各自定義:

| token | 值 | 用途 |
|---|---|---|
| `--dur-fast` | 120ms | hover、顏色變化、小回饋 |
| `--dur-base` | 200ms | 一般狀態切換、展開收合 |
| `--dur-slow` | 320ms | 頁面/面板切換、較大位移 |
| `--ease-out` | `cubic-bezier(0.22, 1, 0.36, 1)` | 大多數進場(快進慢出,俐落) |
| `--ease-in-out` | `cubic-bezier(0.65, 0, 0.35, 1)` | 位移、morph |
| `--ease-spring` | `cubic-bezier(0.34, 1.56, 0.64, 1)` | 需要一點彈性回饋時(節制使用) |

### 6.2 各情境規範

**Hover / 點擊回饋**
- 按鈕、卡片、節點 hover:`--dur-fast`,輕微上浮(`translateY(-1~2px)`)或亮度變化。
- 點擊(`:active`):`scale(0.96~0.98)`,給實體按壓感。
- 統一原則:同類元件用同一種回饋,不要一個按鈕上浮、另一個變色。

**按鈕 hover**
- 全系統按鈕共用同一套 hover:**底色位移 + 陰影**,四個變體只差位移後的顏色。按鈕本身**不做上浮**(卡片才上浮,見上一條)。
- 位移方向依底色決定,不是一律加深:primary 的藏青已經很暗,要往**亮**的方向走(`ink 88% + white`)才看得出變化;ghost/danger 這種淺底或透明底才是加深。判準是「看得出來變了」,不是「一律加深」。
- `:active` 一律 `scale(0.96)`,寫在 hover 規則之後。
- hover 規則整組包在 `@media (hover: hover) and (pointer: fine)` 內:觸控裝置點一下會觸發 hover 並卡在 hover 態。
- 實作在 [AppButton.vue](../frontend/src/components/ui/AppButton.vue),不要在個別頁面另外寫按鈕 hover。

> **邊緣反光(specular hover)已放棄。** 早期版本規定反光沿邊框細線跟隨滑鼠、用 mask-composite + `pointermove` 實作。實測結論:效果做在 1px 邊框上,不論光斑或角度掃描都太細微,使用者根本注意不到;把光帶加寬只會讓它更淡。那套做法適合大顆、深底的單一 CTA,不適合當成六十幾顆按鈕共用的互動語言。不要再回頭做這個。

**展開 / 收合(側邊欄、accordion、workflow 詳情)**
- 寬/高變化:`--dur-base` + `--ease-in-out`。
- 側邊欄收合時,文字 `opacity` 先淡出(`--dur-fast`),寬度再收,避免文字被硬切。

**頁面 / 面板切換**
- 進場:`--dur-slow` + `--ease-out`,輕微上移淡入(`translateY(6~8px)` + `opacity 0→1`)。
- 列表項目可加 stagger(每項延遲 30~40ms 依序進場),但總長不超過 ~250ms,避免拖沓。

**狀態變化(對應成功、載入完成)**
- 徽章/圓點狀態改變時給一次性的輕微強調(如 `scale` 一下或淡入),讓使用者注意到變化。
- 載入用 skeleton(骨架屏)而非空白轉圈,維持版面穩定。

**AI 串流 / 打字**
- AI 回覆逐字/逐段淡入,不要整段瞬間跳出。

### 6.3 效能與可及性

- 玻璃 + 動畫同時作用時,避免同時 animate 多個 `backdrop-filter`(會卡)。
- 大位移用 `transform` / `opacity`(可 GPU 合成),避免 animate `width`/`top` 等觸發 reflow 的屬性(展開收合除外,量小可接受)。
- **必須支援 `prefers-reduced-motion`**:偵測到時關閉非必要動畫。

```css
@media (prefers-reduced-motion: reduce) {
  * { animation: none !important; transition: none !important; }
}
```

## 7. 元件規格

> 以下定義每個元件的「規則與狀態」。具體用 Vuetify 元件改、或自刻,由實作者判斷;重點是產出的結果符合這裡的規範。

### 7.1 按鈕

四種變體,**共用同一套 hover**(見 §6.2),差異只在底色:

| 變體 | 底色 | 文字 | 用途 |
|---|---|---|---|
| primary | `--color-ink-solid` | `--color-inverted` | 主要動作(每個畫面最多一個) |
| secondary | `--color-surface` + `--color-border` inset 邊 | `--color-ink` | 次要動作 |
| ghost | 透明 | `--color-ink-soft` | 輕量動作(略過、取消) |
| danger | `--color-error-bg` | `--color-error-text` | 破壞性動作(移除對應) |
| ai | `linear-gradient(100deg, --color-btn-ai-from, --color-btn-ai-to)` | `--color-inverted` | 觸發 AI 運算的動作,固定帶 `mdi-shimmer` 圖示。只用在明確的 AI 觸發點,不要為了好看套用在一般按鈕上 |

- 形狀:pill(999px)。
- `:active` 一律 `scale(0.96)`。
- 每個畫面最多一個 primary,其餘用 secondary/ghost。
- secondary 的邊界用 `inset box-shadow` 而不是 `border`,免得邊框佔掉尺寸讓它跟其他變體對不齊。
- **primary 與 ai 的底色不引用 `--color-ink` 系列。** 它們是實色深底配淺字,必須在兩個主題都保持深色,所以走 §2.5 的 `--color-ink-solid` 與獨立的 `--color-btn-ai-*`(深色主題各自深一階)。secondary / ghost / danger 沒有這個問題——它們的文字色會跟著主題翻面。
- **主次關係會隨流程階段改變。** 同一顆按鈕在不同狀態下可能該換變體——例如提取框架頁,提取完成後主要動作就從「開始提取」變成「儲存框架」,前者降為 secondary。判準是「使用者此刻最該做什麼」,不是按鈕固定屬於哪一階。
- **`ai` 變體的 loading 不隱藏內容。** 其餘變體 loading 時內容 `visibility: hidden`、置中疊一個圓圈 spinner；`ai` 變體反過來，圖示跟文字維持可見，改成一道低透明度（16%）的光帶斜向掃過底色（2.4s，寬版、慢速）——AI 按鈕的圖示本身是「這是 AI 操作」的語意信號，loading 時蓋掉會失去意義。這個決定是反覆比較過旋轉邊框、公轉光點、脈動光暈、色輪旋轉等做法後定案的,不要回頭嘗試那些方向（見對應 spec 的完整比較過程）。

### 7.2 側邊欄

- 可收合/展開(寬 220px ↔ 72px),收合動畫見 §6.2。
- 玻璃面板浮在漸層背景上(見 §5.2)。淺色主題是淺色玻璃(白色半透明 tint),深色主題是暗場玻璃,跟著全站主題走。
- **側邊欄底部是全站唯一的主題切換入口。** 它原本是 dev-only 的玻璃變體開關,深色模式做完後轉正成使用者可見的「深色模式」開關(`role="switch"`)。`/style-guide` 另有一顆,因為那頁不在 Hub 版面裡、沒有側邊欄可用。
- 兩種變體靠一組語意變數(`--nav-fg`、`--nav-surface-hover`、`--nav-surface-active`、`--nav-border` 等)切換,只換這組值,文字色/hover 底/選中滑塊/分隔線就會一起走。新增側邊欄元素時要用這組變數,不要硬寫顏色,否則深色模式會漏掉。
- **可讀性優先**:靠底色不透明度保證對比,**不用文字陰影**。
- 側邊欄是浮動卡片(`--radius-lg` + `--shadow-float`),上下左三邊留白、不貼齊視窗邊緣;右邊不留,否則會跟主內容自己的 padding 疊成不對稱的留白。
- 選中項:**凹陷**效果 + Medium 字重。帶藏青的淺色底,上緣 inset 陰影、下緣 inset 亮線,光源方向比照 §4.3 由上往下,看起來像刻進玻璃面板裡。
- hover:輕微變亮的半透明白底,`--dur-fast`。**選中與 hover 互為反向**——hover 浮起、選中壓下去,同一套物理語言。
- 選中項不疊 hover 底色:兩層半透明疊在一起會糊掉,底色本身也已由選中滑塊負責。
- 選中指示用單一滑塊在項目間位移(`transform` + `--ease-in-out`),不是每項各自淡入淡出底色。
- 收合狀態 hover 圖示顯示該頁名稱的浮動提示。

### 7.3 卡片 / 面板

- 一般卡片:實色 `--color-surface`,`--radius-md`,`--shadow-card`。**不玻璃化。**
- 浮動面板(AI chat 等):玻璃(見 §5)。
- 卡片內列表 row:hover 換 `--color-surface-alt` 底。

### 7.4 資料表格

DataMind 有大量表格,規範:

- 容器:`--color-surface` + `--radius-md` + `--shadow-card`,`overflow: hidden` 讓圓角吃到邊。
- 表頭:`--color-surface-alt` 底,`--color-ink-soft` 文字,12px,Bold(700,見 §3 資料強調例外)。
- 儲存格:14px,`--color-text`,底線 `--color-border`。
- row hover:比表頭**更淡**的一層(`ink 3% + white`),列才會往前浮而不是沉下去。直接用 `--color-surface-alt` 會跟表頭同色、看起來像沉下去。
- 狀態欄用徽章(見 §7.5)。
- 欄位名等 identifier **不用**等寬字型(見 §3)。
- 欄多、需要一眼掃完的表格加 `.ds-table--dense`(13px、padding 收窄)。§7.4 的 14px 是給一般表格的,套在欄位密集的畫面會把列高撐開。
- 欄多時考慮 `table-layout: fixed` + 明確欄寬,或允許水平捲動。
- 共用樣式在 [ds-table.css](../frontend/src/styles/ds-table.css),掛在 `vuetify-final` layer(套進 Vuetify 元件內的表格才不會被蓋掉);外框用 [TableShell.vue](../frontend/src/components/ui/TableShell.vue)。

### 7.5 狀態顯示(徽章 / 圓點)

兩種呈現,依情境選:

- **圓點 + 文字**:資訊密度高的地方(表格、列表)。圓點 8px,實色狀態色,文字用對應深色。
- **徽章 pill**:需要更明顯時。底用 `--color-*-bg`,文字用對應狀態色。

語意固定:綠=已對應、琥珀=待確認、紅=未對應。**不要用狀態色做非狀態的裝飾。**

### 7.6 Workflow

- 節點:圓形(58px,平板 54px、手機 48px)+ 深色 icon(`--color-ink-strong`)+ 細邊框,依**類型**上色(見 §2.3)。深色主題把這個構造翻面(深底 + 亮 icon),同節 §2.3 有詳細規則。
- 節點下方放 label(13px,`--color-text`)。
- 節點間用連接線串起:已流過的線用 `color-mix(--color-accent 38%, transparent)`(1.8px),還沒流到的用 `--color-border-strong`(1.5px),線在節點下層。已流過的線同色也用在 Settings 步驟切換時的高亮圈(`color-mix(--color-accent 26%, transparent)`),都是中性品牌深藍調淡,不額外加新色相跟節點本身的分類色搶。
- 完成狀態:節點右下角疊一個 outline 風格的勾勾徽章(白底 + `--color-success` 細框 + 綠勾),不用陰影也不用粗邊框,靠白底跟任何節點分類色分開。
- 新增/移除節點(如 Settings 面板加減前處理步驟、模型):浮在節點正上方的小圓 icon,旋轉進出場後停留一下消失。新增用節點自己的分類色(`--node-accent`),移除用中性深灰,不額外引入紅/綠。
- Canvas 背景不鋪底色,直接透出頁面漸層,只疊一層點狀紋理(`--canvas-dot`)標示可操作區域;圓角與裁切統一收在外層容器,canvas 本身不設 `border`/`box-shadow`。點紋只是標示「這裡可以操作」,壓到剛好看得見就好——深色主題沿用 `--color-border-strong` 會變成一片明顯的灰點陣,所以另立 token 給了很淡的白(`rgba(255,255,255,0.07)`)。
- **打開頁面時節點要自動置中。** 進場呼叫一次 `fitView`,padding 逐邊給,底部那邊要額外扣掉抽屜的高度(否則節點會被抽屜蓋住)。畫布容器本身不能設超過父層的固定尺寸——那會被父層的 `overflow: hidden` 裁掉,`fitView` 算出來的中心跟看得見的中心對不上,而且因為是裁切不是捲動,`scrollWidth` 也看不出異常。

### 7.7 論文編輯區

- 工具列:`--color-surface-alt` 底,工具鈕 hover 換淡藏青底。
- 內文區:充足留白,`line-height` 1.6~1.7。
- 載入用 skeleton line。

### 7.8 文獻參考

- 列表形式,每筆:`[index]` + 作者 + venue。
- index、venue 用 `--color-ink-soft`,作者用 `--color-text`。
- 內文裡的引用標記(`[1]`)用 `--color-ink-vivid` 推導的淺色 highlight 底 + 同色數字,讓它讀起來是「可點的引用」而不是灰字。滑過時底色再深一階,整組 gate 在 `@media (hover: hover) and (pointer: fine)` 內。
- 點開的來源 popup **靠右對齊**,不遮擋內文;從引用標記拉一條直線連到 popup,線有一次性的描繪動畫(`--dur-slow`,`prefers-reduced-motion` 時關掉)。popup 位置要跟著捲動更新(`scroll` 事件用 capture 監聽,巢狀捲動容器才抓得到),並用 `requestAnimationFrame` 節流。
- 算右緣位置用 `document.documentElement.clientWidth`,**不要用 `window.innerWidth`**——後者含捲軸寬度,會把 popup 推出畫面。

### 7.9 檔案上傳區

共用元件 [FileDropZone.vue](../frontend/src/components/common/FileDropZone.vue),上傳論文與上傳資料集都用它,不要各頁另刻。

- **空狀態與已選檔共用同一個尺寸**(固定 `min-height`),切換時版面不跳。
- 已選檔時整個框變成檔案卡片(圖示 + 檔名 + 大小 + 更換提示),讓「已經有檔案了,再放會覆蓋」一眼看得出來。移除鈕釘在右上角(`position: absolute`),不參與置中排版——否則它會把中間那疊內容拉偏。
- 移除鈕視覺 32px,用透明的 `::after`(`inset: -6px`)把可點範圍撐到 44×44,兼顧觸控尺寸與視覺份量。
- 拖曳中要有明確回饋(邊框與底色加深、文字換成「放開以…」)。`dragenter`/`dragleave` 在滑鼠移到子元素時也會觸發,**用進出計數**才不會誤關。
- 拖入不接受的檔型時顯示提示,並**保留原本已選的檔案**——拖錯一個檔不該把先前選好的弄丟。
- `<input type="file">` 讀完要把 `value` 清掉,否則再選同一個檔案不會觸發 `change`。
- **注意 `--filled` 與 `--over` 的 CSS 權重**:兩者都是單一 class,同權重時後寫的贏,已選檔狀態會蓋掉拖曳中狀態。用 `.drop-zone.drop-zone--over` 疊權重解決。

### 7.10 下拉選單

自刻元件 [CustomSelect.vue](../frontend/src/components/common/CustomSelect.vue),`Teleport` 到 body,套 `.glass-menu`(玻璃的折衷做法見 §5.3)。

- **已選項只用兩個訊號**:`--color-ink-vivid` 文字色 + Medium 字重,再加一個勾勾圖示。曾經試過再疊左側色條,三個訊號一起上會過度設計,拿掉了——一個狀態不需要三種標示。
- hover(鍵盤 active)用**中性**的 `ink 12%` 淡底,跟已選項的藍色系刻意不同調,兩種狀態才分得開。
- 選項可以被標成 muted(已被其他欄位占用)但仍可點,弱化的文字色仍要過 AA——那是可互動文字,不能用純提示用的淺灰。

### 7.11 捲軸

自訂捲軸樣式時,**`scrollbar-color` 與 `::-webkit-scrollbar` 必須同步修改**。

現代 Chrome 支援標準的 `scrollbar-color`,而且它的優先權**高於** `::-webkit-scrollbar` 偽元素——只改後者完全不會生效。這個坑實際踩過:改了 `::-webkit-scrollbar-thumb` 但捲軸還是原本的顏色,查了兩輪才發現真正生效的是上面那行。兩邊都要寫,而且值要一致。

另外:CSS 規範裡設了 `overflow-x: auto` 會讓 `overflow-y` 隱含變成 `auto`。只想要橫向捲動的容器,要明確寫 `overflow-y: hidden`,否則會多出一條沒用的縱向捲軸。

### 7.12 AI 進行中狀態

- 思考中的區塊用**跑動的漸層邊框**(`::before` + `mask-composite: exclude` 做出只有邊框的漸層),不要用實線 border。
- 漸層的兩端與中段要有**足夠的濃淡差**才看得出在動。曾經用兩端都接近 `--color-ink` 的近黑漸層,色相變化太小,動畫等於沒跑、讀起來就是一條實線。現行用 `--color-ink-vivid` 藍,兩端透明度 20%、中段 75%。
- 逐段思考文字用淡入切換,上一段保留成更小更淡的一行,讓使用者感覺到進度。

## 8. 響應式 / 版面寬度(RWD)

**現況問題**:各頁面各自寫 max-width / breakpoint(760px、80%、88%、1260px…各頁不一樣),窄螢幕還堪用,但螢幕夠寬時內容被拉到滿版,頁面之間比例也對不齊。這節把規則收斂成一份,不要各畫面各自決定。

### 8.1 斷點

沿用 `vuetify.ts` 既有的 `display.thresholds`,不要另開一套斷點系統:

| 斷點 | 寬度 |
|---|---|
| xs | 0 |
| sm | 600px |
| md | 840px(`mobileBreakpoint`,小於此視為行動裝置版面) |
| lg | 1145px |
| xl | 1545px |
| xxl | 2138px |

### 8.2 內容寬度上限(解決「太寬」的關鍵)

版面容器一律有寬度上限,超過就**置中、兩側留白**,不要讓卡片、表格、表單無限拉伸到瀏覽器邊緣。依內容型態分三級,實作時比照色彩/圓角橋接成 token,不要每頁各寫一個數字:

| token | 建議值 | 用途 |
|---|---|---|
| `--content-measure` | 760px | 純文字閱讀區(論文內文、長文說明)。控制單行字數,過寬會難讀 |
| `--content-max-width` | 1280px | 一般頁面容器(表單、Hub 詳情頁、設定)。原訂範圍 1280–1440px,取下限 |
| `--content-max-width-wide` | 1680px | 資料密集頁(大型表格、多欄卡片、workflow 外框) |

> workflow 畫布本身如果是可縮放/可捲動的無限畫布,不受此限——這裡限制的是畫布「外面」的頁面殼(頂部工具列、side panel 等容器)。

### 8.3 斷點下的行為

- **< md(840px)**:側邊欄預設收合或改抽屜(overlay)開合;多欄 grid 改單欄堆疊;字級/間距可視情況降一階。
- **md–xl**:標準單欄或雙欄版面,元件依 §7 規格呈現。
- **≥ xxl(2138px)**:不要讓 grid 欄數或卡片寬度隨螢幕無限放大——鎖住 §8.2 的寬度上限,多出來的空間單純留白,不要靠拉伸元件本身撐版面。

### 9.2 改動時的檢查清單

- **色值一律引用 token**,不要在元件裡硬寫 hex。需要變化用 `color-mix(in oklab, var(--color-x) N%, ...)`。
- **改狀態色**:圓點色與文字色是兩個值,要一起改、一起量對比(§2.2 的對比表)。
- **加 hover**:整組包在 `@media (hover: hover) and (pointer: fine)` 內。
- **加動畫**:用 §6.1 的 token,不要自己寫時長與緩動。注意 `animation-fill-mode` 用 `both`/`forwards` 會把結束時的 `transform` 永久鎖在元素上,後續的 `:hover` 位移就失效了——進場動畫要用 `backwards`。
- **字重只有 400/500**(唯一例外見 §3)。
- **改完開 `/style-guide` 看一遍**,再看實際頁面。**兩個主題都要看**,`/style-guide` 右上角與 Hub 側邊欄底部都有切換鈕。
- **深色模式**:寫死的 hex / `rgba()` 一律換成 token 或 `color-mix`;實色深底用 `--color-ink-solid` 不用 `--color-ink`;`color-mix(..., white)` 改混 `var(--color-surface)`;原生控制項靠 `color-scheme` 不要寫死 `light`。完整規則見 §2.5。

### 9.3 維護這份文件

- **新增顏色 / 新增共用元件 / 改掉既有規範時,回來更新這裡**,尤其 §2.2 色票表與 §2.3 節點色表。文件跟程式碼對不上的時候,它就從「唯一真相」退化成「誤導來源」。
- **記錄「為什麼」,不只記「是什麼」。** 這份文件裡最有價值的部分是那些「曾經試過 X,因為 Y 所以改成 Z」的段落——它們阻止後人重蹈覆轍。色值本身看程式碼就有了,判斷過程只有寫下來才留得住。
- 規範沒寫到的臨場狀況,用 §1 的五個原則判斷,選更安靜、更一致、更可讀的那個做法。
